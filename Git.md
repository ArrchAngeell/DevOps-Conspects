# Мой конспект по Git

Это мои заметки по Git для подготовки на DevOps. Пишу простыми словами, но так, чтобы это можно было почти дословно сказать на собесе. В каждой теме: **как я это понимаю** (для себя, простыми словами) и **что говорю на собесе** (коротко и правильно). Все команды проверяю в тестовой папке.

## 1. Что такое Git

**Как я это понимаю.** Git запоминает историю изменений файлов. Я могу вернуться к любой версии, пробовать идеи отдельно от основной версии и работать в команде, не затирая чужое. Моя аналогия (в документации так не говорят): коммит - это точка сохранения в игре.

**Что говорю на собесе.**
- Git - это распределённая система контроля версий (DVCS): у каждого разработчика на компьютере полная копия репозитория с историей.
- **Git и GitHub - это не одно и то же.** Git программа, а GitHub, GitLab и Bitbucket сервисы, которые хранят репозитории на сервере и добавляют удобства (pull request, ревью, CI).

Три места, где живут файлы:

| Место | Что это | Как файл туда попадает |
|---|---|---|
| Рабочая папка | Мои файлы, которые я правлю | Просто правлю |
| Staging (индекс, «коробка») | Что войдёт в следующий коммит | `git add` |
| Репозиторий | История коммитов (папка `.git`) | `git commit` |

Дальше история уезжает на сервер командой `git push`, а чужая приезжает командой `git pull`.

Главные слова:

- **Коммит** - это снимок состояния проекта с автором, датой, сообщением и уникальным **хэшем** (по умолчанию SHA-1, 40 символов; в командах хватает первых 7).
- **Ветка** - это указатель на коммит. Поэтому ветки дёшево создавать.
- **HEAD** - это указатель на то, где я сейчас: обычно на текущую ветку, а через неё на её последний коммит.

## 2. Основной цикл

**Как я это понимаю.** Правлю файл, кладу в коробку, запечатываю коробку коммитом. Цикл «правка, `add`, `commit`» я буду повторять тысячи раз.

```bash
git init                           # превратить папку в репозиторий
git status                         # что изменилось, что в коробке
git add файл                       # в коробку (git add . = всё в папке)
git commit -m "сообщение"          # сохранить (пишу так, чтобы через месяц было понятно)
git log --oneline                  # короткая история (флаг слитно: --oneline)
git log --oneline --graph --all    # история со всеми ветками
git diff                           # что изменил, но ещё не добавил
git diff --staged                  # что лежит в коробке
git show ХЭШ                       # что изменил конкретный коммит
```

`.gitignore` - это список шаблонов файлов, которые Git не сохраняет (пароли, `node_modules`, логи). Он не действует на файлы, которые уже под контролем Git. Чтобы убрать такой файл из Git, но оставить на диске: `git rm --cached файл`.

**Что говорю на собесе.** `add` кладёт изменения в staging, `commit` сохраняет их в историю, `push` отправляет историю на сервер. Это три разных шага.

## 3. Настройка (один раз)

```bash
git config --global user.name "Имя"
git config --global user.email "почта"
git config --global init.defaultBranch main
git config --global core.editor nvim
```

Имя и почта попадают в каждый коммит и видны всем, если репозиторий публичный.

## 4. Ветки (branches)

**Как я это понимаю.** Ветка - это параллельная линия истории. Хочу попробовать новую фичу: создаю ветку и работаю там. Основная ветка (`main`) при этом остаётся нетронутой. Получилось, вливаю ветку обратно. Не получилось, выбрасываю.

```bash
git branch                    # список (звёздочка = текущая)
git switch -c имя             # создать ветку и перейти в неё
git switch имя                # перейти
git branch -d имя             # удалить после слияния (-D удалит и неслитую)
git branch -M main            # переименовать текущую в main
git push origin --delete имя  # удалить ветку на сервере
```

**`switch` и `checkout`.** Раньше всё делала команда `git checkout` (и переключала ветки, и восстанавливала файлы). В Git 2.23 её обязанности разделили: `git switch` переключает ветки, `git restore` восстанавливает файлы. `checkout` по-прежнему работает, поэтому в старых инструкциях я её встречу.

**Detached HEAD.** Если перейти прямо на коммит или тег (`git switch --detach ХЭШ`), HEAD указывает на коммит без ветки. Новые коммиты там легко потерять. Сохранить работу: `git switch -c имя`.

**Что говорю на собесе.** Ветка - это указатель на коммит. Зачем: изолировать работу над фичей или исправлением. Стабильной `main` её делает договорённость в команде, а не сам Git.

## 5. Слияние (merge)

**Как я это понимаю.** Я доволен веткой и хочу влить её в `main`. Перехожу в ту ветку, **куда** вливаю, и сливаю.

```bash
git switch main
git merge feature-1
git merge --squash feature-1  # собрать все изменения ветки в одну пачку (потом нужен commit)
```

Два исхода:

- **Fast-forward.** Если `main` с момента создания ветки не менялся, Git просто сдвигает указатель вперёд. Нового коммита нет, слияния как такового не происходит.
- **Merge commit.** Если обе ветки получили новые коммиты, Git создаёт отдельный коммит слияния с двумя родителями.

**Что говорю на собесе.** При `merge` меняется только целевая ветка, история исходных веток остаётся как есть.

## 6. Конфликт слияния (merge conflict)

**Как я это понимаю.** Конфликт - это просьба Git «реши сам». Две ветки изменили **одно и то же место** по-разному, и он не знает, какой вариант выбрать. Если изменены разные места файла, Git сольёт их сам.

Типичные примеры: правка одной строки в обеих ветках; файл удалён в одной ветке и изменён в другой. Это только примеры, ситуации бывают разные. Для конфликта не нужны два человека: хватит двух моих веток.

В файле появятся метки (по 7 символов):

```
<<<<<<< HEAD
версия из текущей ветки
=======
версия из вливаемой ветки
>>>>>>> имя-ветки
```

**Как решаю (по шагам, это любят спрашивать):**

1. `git status` покажет конфликтные файлы.
2. Открываю файл и решаю, какой вариант нужен (или объединяю оба).
3. Оставляю нужное, удаляю ненужное **и все три строки с метками**.
4. `git add файл` (так я говорю Git, что конфликт решён).
5. `git commit` (редактор откроется с готовым сообщением, просто сохраняю).

Передумал: `git merge --abort` вернёт всё как до слияния. При `rebase` вместо коммита делаю `git rebase --continue` (или `--abort`).

## 7. Откат изменений

**Как я это понимаю.** Сначала определяю, **где** то, что я откатываю: в файле, в коробке или уже в коммите. От этого зависит команда.

| Ситуация | Команда | Что происходит |
|---|---|---|
| Выбросить правки в файле (коммита нет) | `git restore файл` | Файл возвращается к сохранённому виду. **Правки пропадают навсегда** |
| Убрать из коробки, правки оставить | `git restore --staged файл` | Файл уходит из staging, в файле всё осталось |
| Отменить уже сделанный коммит | `git revert ХЭШ` | **Новый** коммит, который отменяет старый. История не переписывается |
| Поправить последний коммит (он не запушен) | `git commit --amend` | Последний коммит заменяется новым |

**Что говорю на собесе.**
- `restore` работает с **файлами** и коммитов не трогает.
- `revert` работает с **коммитами** и не переписывает историю, поэтому безопасен в команде и подходит для уже отправленных коммитов.
- `--amend` переписывает последний коммит (у него новый хэш), поэтому не делаю его для уже запушенных коммитов.

### reset

`git reset` двигает ветку назад по истории. Три режима:

| Режим | Что происходит с изменениями |
|---|---|
| `--soft` | Остаются в коробке (staging) |
| `--mixed` (по умолчанию) | Уходят из коробки, остаются в файлах |
| `--hard` | Стираются и из файлов. **Несохранённое обычно не вернуть** |

Откат всего репозитория к определённому коммиту: `git reset --hard ХЭШ`. Это для локальной работы. На запушенных ветках, которыми пользуются другие, так не делаю: нужен `revert`.

## 8. Перенос коммитов между ветками

**Как я это понимаю.** Три способа забрать работу из одной ветки в другую:

- **`git merge`**: влить ветку целиком.
- **`git cherry-pick ХЭШ`**: взять один конкретный коммит (или несколько). Сначала перехожу в ветку, **куда** переношу.
- **`git rebase`**: переложить коммиты своей ветки поверх свежей версии другой, как будто я начал работу позже.

```bash
git switch main
git cherry-pick 1a2b3c4            # хэш из git log --oneline
# при конфликте: решаю, git add, затем:
git cherry-pick --continue         # или --abort

git switch feature-1
git rebase main                    # положить коммиты feature-1 поверх свежего main
```

**Как выглядит разница:**

```
Было:           A - B - C          (main)
                     \
                      D - E        (feature)

После merge:    A - B - C - F      (F = коммит слияния)
                     \     /
                      D - E

После rebase:   A - B - C - D' - E'   (новые коммиты D' и E', история прямая)
```

**Что говорю на собесе: merge и rebase.**

- `merge` сохраняет историю как есть, при необходимости создаёт коммит слияния. Просто и безопасно.
- `rebase` перекладывает коммиты по одному на новую базу, и у них **новые хэши**. История становится прямой, но **переписывается**.
- Нельзя делать `rebase` над ветками, которые **уже отправлены на сервер и которыми пользуются другие**: у остальных остаются старые хэши, и истории расходятся. На своей локальной ветке, пока я её не отправлял, `rebase` нормален.
- Если сомневаюсь, использую `merge`.
- После `rebase` ветки, которая уже была на сервере, нужен принудительный пуш, лучше `--force-with-lease`.

Распространённая ошибка в сборниках: что `rebase` «сжимает всё в один патч». Это неверно. `rebase` переносит коммиты по одному. Объединить несколько коммитов в один можно отдельно, интерактивным `rebase` (`git rebase -i HEAD~3`, действие `squash`), или через `merge --squash`.

## 9. Теги (tags)

**Как я это понимаю.** Тег - это именная метка на конкретном коммите, обычно номер версии (`v1.0`, `v2.0`). Она не двигается.

```bash
git tag                          # список тегов
git tag v1.0                     # лёгкий тег на текущем коммите
git tag -a v1.0 -m "Релиз 1.0"   # аннотированный тег (с автором, датой, сообщением)
git push origin v1.0             # отправить тег (git push --tags отправит все)
```

Версии принято писать по схеме **semver**: МАЖОР.МИНОР.ПАТЧ (например, `2.3.1`): мажор растёт при несовместимых изменениях, минор при новых возможностях, патч при исправлениях.

**Что говорю на собесе: чем `tag` отличается от `branch`.**
- И тег, и ветка это указатели на коммиты.
- **Ветка движется:** с каждым новым коммитом в ней указатель сдвигается вперёд.
- **Тег стоит на месте:** он навсегда указывает на один коммит, поэтому подходит для релизов.
- Есть лёгкие теги (просто указатель) и аннотированные (хранят автора, дату и сообщение, их используют для релизов).

## 10. Удалённый репозиторий

**Как я это понимаю.** Удалённый репозиторий - это копия на сервере (GitHub). По умолчанию её называют `origin`.

```bash
git clone git@github.com:ник/репо.git   # скачать репозиторий целиком
git remote -v                           # куда смотрит origin
git remote add origin АДРЕС             # привязать
git remote set-url origin НОВЫЙ_АДРЕС   # сменить адрес
git push -u origin main                 # отправить; -u запоминает связь, потом хватит git push
git fetch                               # скачать новое, ничего не меняя в моих файлах
git pull                                # = git fetch + git merge
git pull --rebase                       # = git fetch + git rebase (без коммита слияния)
```

**Что говорю на собесе: `fetch` и `pull`.**
- `fetch` скачивает новые коммиты с сервера и кладёт их в локальные «удалённые» ветки (`origin/main`). Мои ветки и файлы не меняются, можно сначала посмотреть, что пришло.
- `pull` это `fetch` и сразу `merge` в текущую ветку. Удобнее, но может неожиданно вызвать конфликты, если я не смотрю, что пришло.

**Почему `push` отклоняют** (`rejected`, `fetch first`, `non-fast-forward`): на сервере есть коммиты, которых нет у меня, поэтому Git не может просто добавить мои сверху. Решение: `git pull`, при необходимости решить конфликты, затем `git push`.

`git push -f` перезаписывает историю на сервере. В личном репозитории допустимо, в командном нельзя: можно стереть чужую работу. Безопаснее `--force-with-lease`: он откажет, если на сервере появилось то, чего я не видел.

**HTTPS или SSH.**
- `https://...` требует токен (пароль аккаунта GitHub для Git не принимается).
- `git@github.com:...` работает по SSH-ключу.

**Fork, clone, pull request.**
- **`clone`** копирует репозиторий на мой компьютер.
- **Fork** - это копия чужого репозитория на сервере под моим аккаунтом (возможность GitHub и GitLab).
- **Pull request** (на GitLab он называется **merge request**) это заявка «влейте мои изменения»: коллеги смотрят код, запускаются проверки, и только потом ветка вливается.

## 11. Полезные мелочи: stash

**`git stash`** прячет незакоммиченные правки «в карман», чтобы сменить ветку или срочно что-то поправить, а потом вернуть.

```bash
git stash                 # спрятать правки (новые, неотслеживаемые файлы: git stash -u)
git stash list            # что спрятано
git stash pop             # вернуть последнюю заначку и удалить её из списка
git stash apply           # вернуть, но оставить заначку в списке
git stash drop            # удалить заначку
```

## 12. Стратегии ветвления (workflow)

**Как я это понимаю.** Стратегия ветвления это набор командных правил: какие ветки живут всегда, как их называть, откуда создавать и когда можно сливать. Сам Git правил не навязывает.

| Стратегия | Суть |
|---|---|
| **GitFlow** | Две долгоживущие ветки: `main` (готово к релизу) и `develop` (интеграция). Для задач ветки `feature` от `develop`, для подготовки релиза `release`, для срочных исправлений на проде `hotfix` от `main` |
| **GitHub Flow** | Одна главная ветка, она всегда готова к деплою. Для каждой задачи короткая ветка, затем pull request, ревью, слияние и деплой |
| **Trunk-Based Development** | Все работают в одной главной ветке (trunk, ствол). Побочные ветки живут очень недолго (часы или день-два), изменения маленькие, часто сливаются. Недоделанное прячут за **feature flag** (переключатель, включающий или выключающий фичу) |

**GitFlow по шагам:**
1. От `main` создаётся `develop`.
2. От `develop` создаются ветки `feature`; готовая фича вливается обратно в `develop`.
3. Для релиза от `develop` создаётся `release`; когда готова, вливается и в `main`, и в `develop`.
4. Если в `main` нашли проблему, от него создаётся `hotfix`; после исправления вливается и в `main`, и в `develop`.

**Что говорю на собесе: что выбрать.** GitFlow подходит для проектов с чёткими релизами, но тяжёлый. Для частых релизов и CI/CD обычно берут GitHub Flow или Trunk-Based: меньше долгоживущих веток, меньше болезненных конфликтов. Если сомневаюсь, называю причину выбора, а не просто название.

## 13. Git в DevOps

- **CI/CD запускается по событиям Git:** по `push` в ветку, по pull request, по тегу (например, тег `v1.2.0` запускает сборку релиза).
- **Защита веток (protected branches)** это настройка на сервере: в `main` нельзя пушить напрямую, нужны pull request, ревью и зелёные проверки.
- **Теги** отмечают версии, которые собрали и выложили.
- **Секреты в Git:** пароль, ключ или токен, попавший в коммит, остаётся в истории, даже если файл потом удалить. Такой секрет считаю скомпрометированным и меняю.

## 14. Мои грабли и частые ошибки в ответах

Грабли из практики:

- Репозиторий на GitHub создан с лицензией или README, а локально свой репозиторий: истории разъехались, `push` отклоняют. Удалённый репозиторий создаю **пустым**.
- Добавил `remote` по HTTPS и получил `Invalid username or token`: сменил адрес на SSH.
- `git log --one-line` не работает: правильно `--oneline`.
- Перед первым коммитом смотрю `git status` и список файлов: нет ли токенов и ключей. В публичном репозитории всё видно всем.
- Предупреждение `LF will be replaced by CRLF` на Windows безвредно для `.md`, но опасно для скриптов (на Linux ломается `#!/bin/bash`).

Ошибки, которые я делал в ответах (запомнить, как правильно):

- После `add` нужен **`commit`**, а `push` отдельно. Слияние завершается коммитом, а не отправкой.
- `restore` не про коммиты, он про файлы.
- `reset --hard` не «удаляет файлы», он приводит файлы к состоянию коммита и **стирает несохранённые правки**.
- `fast-forward` - это не слияние с новым коммитом, а просто сдвиг указателя.
- HEAD - это не «последняя ветка, где были изменения», а **где я сейчас**.
- `rebase` не «двигает ветку вперёд», а **перекладывает коммиты** (новые хэши), и его нельзя применять к опубликованным общим веткам.
- `--oneline` пишется слитно.
- Тег и ветка: ветка двигается, тег стоит на месте.

## 15. Шпаргалка: ситуация и команда

| Ситуация | Команда |
|---|---|
| Выбросить правки в файле | `git restore файл` |
| Убрать из staging | `git restore --staged файл` |
| Отменить сделанный коммит безопасно | `git revert ХЭШ` |
| Поправить сообщение последнего коммита (не запушен) | `git commit --amend` |
| Откатить локально всё к коммиту | `git reset --hard ХЭШ` |
| Перенести один коммит в другую ветку | `git cherry-pick ХЭШ` |
| Убрать файл из Git, но оставить на диске | `git rm --cached файл` |
| Посмотреть, что пришло с сервера, не меняя файлы | `git fetch` |
| Решить конфликт | править файл, `git add`, `git commit` |
| Отменить слияние в процессе | `git merge --abort` |
| Пометить релиз | `git tag -a v1.0 -m "..."` |
