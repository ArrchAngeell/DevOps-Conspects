# Мой конспект по Linux

Это мои заметки для подготовки на DevOps. Пишу простыми словами, но так, чтобы это можно было почти дословно сказать на собесе. В каждой теме: **как я это понимаю** (для себя, простыми словами) и **что говорю на собесе** (коротко и правильно). Все команды проверяю в своём Debian.

## 1. Файловая система и навигация

**Как я это понимаю.** В Linux нет дисков `C:` и `D:`. Всё растёт из одного корня `/`, а диски «подключаются» к папкам (монтируются). Почти всё устроено как файл: данные, папки, устройства, сокеты, каналы.

| Папка | Что там |
|---|---|
| `/home` | Домашние папки (`~` это моя) |
| `/etc` | Настройки |
| `/var/log` | Логи |
| `/tmp` | Временные файлы |
| `/usr/bin` | Программы |
| `/boot` | Ядро и всё для загрузки |
| `/dev` | Устройства как файлы |
| `/proc` | Данные ядра и процессов (не настоящие файлы) |
| `/sys` | Ещё один интерфейс к ядру и устройствам (в том числе cgroups) |
| `/mnt/c` | Мой диск C: из Windows (только в WSL) |

```bash
pwd                   # где я
ls -lah               # список с правами, размерами, скрытыми файлами
cd -                  # в прошлую папку; cd без аргументов: домой
mkdir -p a/b/c        # вложенные папки
cp -r A B             # копировать
mv A B                # переместить или переименовать
rm -r папка           # удалить со всем содержимым (корзины нет!)
rm -- -rf             # удалить файл с именем «-rf» (-- значит «дальше не опции»)
cat файл              # показать целиком
less файл             # по страницам (/слово поиск, q выход)
tree                  # дерево папок
stat файл             # размер, права, inode, времена (изменения, доступа, смены)
stat --format=%y файл # только время последней модификации
file файл             # определить тип файла по содержимому
type команда          # программа, алиас или встроенная команда
man команда           # справка (нужен man-db); man 2 имя = про системный вызов
```

Поиск:

```bash
find /var/log -name "*.log" -mtime -1    # файлы по имени, изменённые за сутки
find . -size +100M                       # большие файлы
locate имя                               # быстрый поиск по базе (нужен updatedb)
rg "текст" папка                         # поиск по содержимому
```

**Ссылки (`ln`).**

| | Жёсткая (`ln A B`) | Символическая (`ln -s цель ссылка`) |
|---|---|---|
| Что это | Ещё одно **имя** того же файла (тот же inode) | Отдельный маленький файл с путём к цели |
| Удалил оригинал | Данные живут, пока есть хоть одно имя | Ссылка «ломается» |
| Между ФС | Нельзя | Можно |
| На папку | Нельзя | Можно |
| Как увидеть | `ls -li` (одинаковый inode, счётчик ссылок) | `ls -l` (буква `l`, стрелка `->`) |

**Что говорю на собесе.** Жёсткая ссылка это второе имя файла, а не копия: изменения видны через оба имени, файл удаляется, когда счётчик имён дошёл до нуля. Символическая ссылка это ярлык-путь: если цель удалить, ссылка висит «битой».

## 2. Права и пользователи

**Как я это понимаю.** У каждого файла есть владелец, группа и «все остальные», и для каждого из трёх свои права: читать, писать, запускать.

`ls -l` показывает, например, `-rwxr-xr--`: первый символ тип (`-` файл, `d` папка), дальше три тройки (владелец, группа, остальные).

| Символ | Число | Файл | Папка |
|---|---|---|---|
| `r` | 4 | читать | видеть список файлов |
| `w` | 2 | менять | создавать и удалять файлы в ней |
| `x` | 1 | запускать | **заходить в неё** |

- `755` = `rwx r-x r-x` (папки и программы), `644` = `rw- r-- r--` (обычные файлы), `700` = только владельцу.
- **Как система проверяет права:** сначала владелец ли я (если да, применяются права владельца и дальше не смотрит), потом вхожу ли в группу, и только потом «остальные». То есть права владельца могут быть строже прав группы.
- Чтобы дойти до файла, нужно `x` на **каждой папке по пути**. Если файл «не найден» или «Permission denied», хотя он на месте, проверяю путь: `namei -l путь`. Это я уже ловил на практике с `~` (права 700).
- Права на запись «всем» (`767`, `777`) на скриптах опасны: любой пользователь может подменить код.
- `umask` (обычно 022) задаёт права по умолчанию: файлы 644, папки 755.

**Особые биты:**

| Бит | Для файла | Для папки |
|---|---|---|
| **setuid** (4) | Запускается с правами **владельца**, а не запустившего (пример: `passwd` меняет `/etc/shadow`) | не используется |
| **setgid** (2) | Запускается с правами **группы** файла | Новые файлы в папке наследуют её группу |
| **sticky** (1) | не используется | Удалять и переименовывать файл может только его владелец (пример: `/tmp`) |

```bash
chmod 755 файл        # числом
chmod +x script.sh    # добавить право запуска
chmod u+s файл        # setuid
chown user:group файл
whoami; id            # кто я, мои группы
```

**Пользователи и sudo.**

- Данные: `/etc/passwd` (пользователи), `/etc/shadow` (хэши паролей, читает только root), `/etc/group` (группы). Команды: `adduser`, `usermod -aG группа пользователь`, `passwd`.
- **root** (UID 0) может всё, постоянно под ним работать небезопасно.
- `sudo команда` выполняет команду от имени другого пользователя (по умолчанию root), спрашивает **мой** пароль и сверяется с правилами в `/etc/sudoers` (правлю через `visudo`, он проверяет синтаксис). `sudo -l` покажет, что мне разрешено, `sudo -u user команда` выполнит от имени `user`.
- `su` переключает пользователя целиком и просит пароль **того**, на кого переключаюсь.
- Кто вошёл в систему: `who`, `w` (ещё и чем заняты), `last` (история входов).

## 3. Потоки, перенаправления, пайпы, текст

У каждого процесса три стандартных потока (файловых дескриптора):

| № | Имя | Что это | По умолчанию |
|---|---|---|---|
| 0 | stdin | ввод | клавиатура |
| 1 | stdout | обычный вывод | терминал |
| 2 | stderr | сообщения об ошибках | терминал |

```bash
cmd > файл          # stdout в файл (перезапись)
cmd >> файл         # дописать в конец
cmd < файл          # stdin из файла
cmd 2> err.txt      # только ошибки в файл
cmd 2>/dev/null     # выбросить ошибки
cmd > out.txt 2>&1  # и вывод, и ошибки в один файл (порядок важен: 2>&1 после >)
cmd &> файл         # то же коротко (bash)
cmd 2>&1 >/dev/null | grep слово   # отфильтровать ТОЛЬКО ошибки
```

Последняя строка читается так: сначала stderr отправляю туда, куда сейчас смотрит stdout (в пайп), потом stdout выбрасываю. Если поменять порядок, получится не то.

**Пайп `|`** подключает stdout одной команды к stdin другой. Обе команды запускаются одновременно, данные идут через буфер в ядре. Через пайп идёт **только stdout**; чтобы пустить и ошибки, делаю `команда1 2>&1 | команда2` или короче `команда1 |& команда2`. Если читающая сторона закрылась, пишущая получает SIGPIPE.

**Файловый дескриптор** это неотрицательное число, по которому процесс обращается к открытому файлу, сокету, пайпу или устройству. Данные о позиции и режиме открытия хранит ядро (смотрю в `/proc/PID/fdinfo`). Три стандартных (0, 1, 2) есть у каждого процесса. Открытые файлы процесса: `ls -l /proc/PID/fd`.

**Текстовые инструменты** (без них не разобрать логи):

```bash
grep -i error файл          # строки со словом (-i без учёта регистра, -r по папке)
cut -d: -f1 /etc/passwd     # колонка по разделителю
awk '{print $1}' файл       # поле по номеру
sed 's/старое/новое/g'      # замена
sort -n / sort -r           # сортировка числовая / обратная
uniq -c                     # посчитать повторы (вход должен быть отсортирован)
wc -l                       # сколько строк
xargs                       # превратить stdin в аргументы команды
tee файл                    # писать и в файл, и дальше по пайпу
jq '.поле'                  # разбор JSON
```

Типичная цепочка для логов:

```bash
journalctl --no-pager -n 500 | grep -i error | awk '{print $5}' | sort | uniq -c | sort -rn | head
```

**Кавычки: одинарные и двойные.**

| | `'...'` | `"..."` |
|---|---|---|
| Переменные | **не подставляются** (`'$HOME'` останется текстом) | подставляются (`"$HOME"`) |
| Подстановка команд | нет | да (`"$(date)"`, старый вариант `` `date` ``) |

Правило для себя: переменные всегда в двойных кавычках (`"$var"`), чтобы пробелы в значении не ломали команду.

## 4. Переменные окружения и bash

**Как я это понимаю.** Переменная окружения это пара «имя=значение», которую программа получает при запуске. Дочерние процессы наследуют только те переменные, которые помечены `export`.

```bash
env                      # все переменные окружения
export VAR=значение      # видна дочерним процессам
VAR=значение             # видна только текущей оболочке
echo "$PATH"             # где ищутся программы (слева направо)
```

- **PATH:** список папок, где оболочка ищет программу по имени. Поэтому `hello.sh` даёт `command not found`, а `./hello.sh` работает: `./` значит «запусти файл отсюда».
- **Файлы настройки оболочки:**
  - `~/.bashrc`: читается интерактивными оболочками (алиасы, приглашение, `PATH`);
  - `~/.bash_profile` и `~/.profile`: читаются при входе (login shell); bash берёт первый найденный из `~/.bash_profile`, `~/.bash_login`, `~/.profile`. В Debian `.profile` подключает `.bashrc`.
  - Применить без перезапуска: `source ~/.bashrc` или `exec bash -l`.

**Специальные переменные bash:**

| Переменная | Значение |
|---|---|
| `$?` | Код возврата последней команды (0 успех) |
| `$$` | PID текущей оболочки или скрипта |
| `$!` | PID последнего процесса, запущенного в фоне |
| `$1`, `$2` | Аргументы скрипта |
| `$#` | Сколько аргументов |
| `$@` | Все аргументы по отдельности (в кавычках `"$@"` сохраняет их границы) |

**Скрипты:**

```bash
#!/bin/bash                    # shebang: чем запускать; в Debian /bin/sh это dash, не bash
set -euo pipefail              # строгий режим (см. ниже)
name="World"                     # без пробелов вокруг =
echo "Hello, $name"

if [[ -f "$1" ]]; then         # -f файл, -d папка, -z пустая строка
  echo "exist"
else
  echo "no" >&2               # в stderr
  exit 1                       # код возврата: 0 успех, не 0 ошибка
fi

for f in *.log; do echo "$f"; done
while read -r line; do echo "$line"; done < файл
check() { [[ -d "$1" ]]; }     # функция, её результат = код возврата
trap 'echo "stopped"' INT TERM  # перехват сигналов в скрипте
```

**Строгий режим и отладка:**

| Что | Зачем |
|---|---|
| `set -e` | Остановить скрипт при ошибке команды |
| `set -u` | Ругаться на необъявленную переменную |
| `set -o pipefail` | Считать ошибкой сбой в любом звене пайпа, а не только последнем |
| `set -x` или `bash -x script.sh` | Режим отладки: печатать каждую команду перед выполнением |
| `команда \|\| true` | Если эта команда упадёт, скрипт со `set -e` продолжит работу |

У `set -e` есть тонкие случаи (например, внутри `if`), так что это не полная защита.

**Подоболочки (subshell).** Каждая часть пайпа и каждая группа в `( ... )` выполняется в отдельном процессе. Поэтому переменная, изменённая там, в родителе не меняется. Пример: `a=5; true | { a=10; echo $a; }; echo $a` выведет сначала `10`, потом `5`.

**Что говорю на собесе.** В Debian `/bin/sh` это dash (быстрее, но без bash-расширений вроде `[[ ]]`), поэтому скрипты с bash-фишками начинаю с `#!/bin/bash`.

## 5. Процессы

Процессы это топ-1 тема на собесах: понимаю процессы, значит понимаю, почему сервис упал, почему сервер тормозит и как это чинить. Разбор типовых поломок в разделе 13.

### 5.1 Основы и особые PID

**Как я это понимаю.** Процесс это запущенная программа. У каждого есть свой номер **PID** и номер родителя **PPID**.

```bash
ps aux                       # снимок всех процессов
ps -eo pid,ppid,stat,cmd     # выбранные колонки
top / htop / btop            # живой список
pstree -p                    # дерево процессов
sleep 300 &                  # запустить в фоне
kill PID                     # SIGTERM (15)
kill -9 PID                  # SIGKILL
```

**Особые PID (спрашивают на собесах, не забыть):**

| PID | Кто это | Что запомнить |
|---|---|---|
| **0** | Внутренний «простаивающий» процесс ядра (idle, исторически swapper), по одному на каждое ядро CPU | Работает, когда нет других задач, и «ничего не делает». В `ps` его **не видно**. Это не swap, а именно idle-задача планировщика |
| **1** | Первый процесс в пользовательском пространстве (у меня systemd; раньше init) | Запускает службы, **родитель всех осиротевших процессов**. Если PID 1 умрёт, ядро упадёт (kernel panic) |
| **2** | `kthreadd` | Родитель потоков ядра (в `ps` они в квадратных скобках) |

Максимум PID задаёт `/proc/sys/kernel/pid_max` (старое значение 32768, на 64-битных системах до 4194304, проверю у себя). Когда PID кончаются, новые процессы не стартуют.

**Процесс и поток.**

| | Процесс | Поток (thread) |
|---|---|---|
| Что это | Программа в работе со своей памятью и ресурсами | Линия выполнения внутри процесса |
| Память | Своя, изолирована от других | **Общая** с другими потоками этого процесса |
| Создание и переключение | Тяжелее | Легче |
| Связь | Через IPC (раздел 5.7) | Прямо через общую память |

В Linux ядро хранит и процессы, и потоки одинаково (как `task_struct`, раздел 5.7). Потоки вижу через `ps -eLf` и `top -H`.

### 5.2 fork, exec, wait: что происходит при `ls -l`

1. Оболочка находит `ls` по `PATH` (встроенные команды вроде `cd` выполняются в самой оболочке без нового процесса, поэтому `cd` и не может быть отдельной программой).
2. `fork()`: оболочка создаёт свою копию (потомка).
3. `exec()`: потомок заменяет себя программой `ls` (PID тот же, код новый).
4. Оболочка-родитель ждёт через `wait()`.
5. `ls` делает работу (системные вызовы `openat`, `getdents`, `write`) и завершается через `exit()`.
6. Родитель получает сигнал **SIGCHLD** («потомок завершился»), забирает код возврата и показывает приглашение.

### 5.3 Состояния

| Код | Название | Смысл |
|---|---|---|
| R | running | Выполняется или ждёт очереди на CPU |
| S | sleeping | Спит, ждёт события (ввода, сети, таймера). Таких большинство, это нормально |
| D | uninterruptible sleep | Ждёт ввода-вывода (диск, NFS), прервать нельзя; считается в load average |
| T | stopped | Остановлен (SIGSTOP, `Ctrl+Z`), вернуть через SIGCONT |
| Z | zombie | Мёртв, запись осталась |

Дополнительные символы в колонке STAT (`Ss`, `Sl+`, `R+`):

| Символ | Значение |
|---|---|
| `s` | лидер сессии |
| `l` | многопоточный |
| `+` | на переднем плане в терминале |
| `<` / `N` | повышенный / пониженный приоритет |

### 5.4 Зомби и сироты

**Как я это понимаю.** Зомби это уже мёртвый процесс, от которого осталась только маленькая запись в таблице процессов. Сирота это живой процесс, у которого умер родитель. Запомнить: у сироты нет родителя, а у зомби нет жизни.

- **Зомби:** процесс завершился, но родитель не вызвал `wait()` и не забрал код возврата. Память зомби уже освобождена, остаётся запись (PID и код возврата). В `ps` у него `Z` и `<defunct>`.
- **Сирота:** родитель умер раньше потомка. Потомка «усыновляет» PID 1, он продолжает работать, ничего страшного.
- **Убить зомби нельзя** (`kill`, даже `kill -9`, не поможет): он уже мёртв, сигнал принимать некому. Лечится так: родитель должен вызвать `wait()`; если родитель завис, его перезапускаю или убиваю, и тогда зомби подбирает PID 1.
- **Чем опасны:** один зомби безвреден, а тысячи забивают таблицу PID, и новые процессы перестают запускаться (`fork: Resource temporarily unavailable`).
- **Как сделать зомби (проверка руками):**

```bash
bash -c 'sleep 1 & exec sleep 30' &
sleep 3
ps -eo pid,ppid,stat,cmd | grep defunct
```

Здесь `exec` заменяет оболочку на `sleep 30`, который не умеет вызывать `wait()`, поэтому завершившийся `sleep 1` остаётся зомби, пока родитель не выйдет.

### 5.5 Сигналы

**Как я это понимаю.** Сигнал это короткое «сообщение» процессу от ядра, другого процесса или пользователя. Всего порядка 64 (список: `kill -l`).

| Сигнал | № (x86) | Смысл |
|---|---|---|
| SIGTERM | 15 | Просьба завершиться (по умолчанию для `kill`), процесс может прибраться |
| SIGKILL | 9 | Убить немедленно, перехватить нельзя, данные могут потеряться |
| SIGHUP | 1 | «Связь оборвалась»; многие службы по нему перечитывают конфиг (nginx, например) |
| SIGINT | 2 | `Ctrl+C` |
| SIGQUIT | 3 | `Ctrl+\` |
| SIGSTOP / SIGCONT | 19 / 18 | Остановить / продолжить (SIGSTOP перехватить нельзя) |
| SIGTSTP | 20 | `Ctrl+Z` |
| SIGCHLD | 17 | Потомок завершился, остановился или продолжился (родитель делает `wait`) |
| SIGSEGV | 11 | Обращение к чужой или несуществующей памяти (segmentation fault) |
| SIGUSR1 / SIGUSR2 | 10 / 12 | Пользовательские, смысл задаёт программа |

**Как процесс обрабатывает сигнал:** действие по умолчанию, игнорирование или собственный обработчик. Исключение: **SIGKILL и SIGSTOP нельзя ни перехватить, ни проигнорировать.**

**Что говорю на собесе про SIGTERM и SIGKILL.** SIGTERM это вежливая просьба: процесс может закрыть файлы, дописать данные и выйти. SIGKILL ядро исполняет само, процесс не успевает прибраться. Сначала `kill`, и только если не реагирует, `kill -9`.

### 5.6 Приоритеты и фоновые процессы

- `nice -n 10 команда`, `renice -n 5 -p PID`: приоритет от -20 (высший) до 19 (низший), по умолчанию 0; повышать приоритет может только root.
- Фон: `команда &`, `jobs`, `fg`, `bg`. `nohup команда &` не умирает при закрытии терминала, `disown` убирает задачу из списка оболочки. Надёжный вариант: `tmux` или `screen`.

### 5.7 task_struct, изоляция и взаимодействие процессов

- **Изоляция.** У каждого процесса своё виртуальное адресное пространство, и один процесс не может прочитать или изменить память другого. Общаться процессы могут только через разрешённые ядром каналы.
- **`task_struct`** это структура данных ядра, описывающая процесс: PID, состояние, родителя, приоритет, память, открытые файлы, права, namespace, cgroup. То, что я вижу в `ps` и `/proc/PID/`, отражение этой структуры.
- **Как процессы общаются (IPC):**

| Способ | Что это |
|---|---|
| Пайп (`\|`) | Канал между связанными процессами, **в одну сторону** |
| Именованный пайп (FIFO, `mkfifo`) | То же, но через файл, можно между несвязанными процессами; тоже в одну сторону |
| Сокеты | Двусторонняя связь: сетевая или локальная (unix socket) |
| Очереди сообщений | Сообщения через ядро |
| Разделяемая память | Общий кусок памяти (быстро, но нужна синхронизация) |
| Семафоры | Синхронизация доступа к общим ресурсам |
| Сигналы | Короткие уведомления |

**Разделяемая память (shared memory)** это область, которую одновременно используют несколько процессов. Примеры: базы данных (общие буферы), веб-серверы, `/dev/shm` (tmpfs в RAM). Посмотреть: `ipcs -m`.

### 5.8 /proc, лимиты и открытые файлы

`/proc` это псевдофайловая система: файлов на диске нет, ядро строит их на лету. `ps aux` и `htop` берут данные оттуда.

| Файл | Что даёт |
|---|---|
| `/proc/PID/cmdline` | Командная строка процесса |
| `/proc/PID/environ` | Окружение процесса |
| `/proc/PID/exe` | Ссылка на запущенный файл |
| `/proc/PID/cwd` | Текущая папка процесса |
| `/proc/PID/fd/` | Открытые файлы и потоки |
| `/proc/PID/fdinfo/` | Позиция и флаги дескрипторов |
| `/proc/PID/limits` | Лимиты процесса |
| `/proc/PID/status` | Состояние, родитель, память, потоки, права |
| `/proc/PID/mounts`, `net` | Смонтированное и сетевое, что видит процесс |
| `/proc/loadavg`, `meminfo`, `cpuinfo`, `cmdline` | Данные по системе (cmdline: параметры загрузки ядра) |

**«Too many open files»: как диагностирую.**

1. Лимит процесса: `grep "Max open files" /proc/PID/limits`; лимит оболочки: `ulimit -n`.
2. Сколько открыто: `ls /proc/PID/fd | wc -l` или `lsof -p PID | wc -l`.
3. Для службы лимит задаётся в unit-файле: `LimitNOFILE=`. Файл `/etc/security/limits.conf` действует на сессии пользователей, на службы systemd обычно нет.
4. Утечка ли: `strace -e trace=openat,close -p PID` (открывает и не закрывает?).
5. Общесистемный предел: `sysctl fs.file-max`.

### 5.9 Пространство пользователя и ядра, системные вызовы

- **Пространство ядра** (kernel space): код ядра, полный доступ к памяти и железу. **Пространство пользователя** (user space): всё остальное (программы, оболочка), доступ ограничен.
- **Системный вызов** это «дверь» из программы в ядро: программа не может сама работать с диском, сетью или процессами, она просит ядро. Процессор при этом переключается из user mode в kernel mode.

| Вызов | Что делает |
|---|---|
| `fork` / `clone` | Создать процесс (современные glibc реализуют fork через clone) |
| `execve` | Заменить программу в процессе |
| `wait4` / `waitpid` | Ждать потомка и забрать код возврата |
| `exit` | Завершить процесс |
| `open` / `openat`, `close` | Открыть и закрыть файл |
| `read`, `write` | Читать и писать (файл, пайп, сокет, терминал) |
| `access` | Проверить права |
| `mmap`, `brk` | Память |
| `socket`, `connect`, `bind`, `listen`, `accept` | Сеть |
| `kill` | Отправить сигнал |

Инструменты: `strace команда` (какие системные вызовы делает), `strace -c команда` (сводка по вызовам и ошибкам), `strace -p PID`, справка `man 2 имя_вызова` (пакет `manpages-dev`). На современной системе вместо `open` и `fork` часто вижу `openat` и `clone`.

## 6. Нагрузка и мониторинг

### 6.1 top и htop

В выводе таблица процессов в реальном времени и параметры, которые сразу дают картину:

| Параметр | Смысл |
|---|---|
| up | Сколько система работает |
| load average | Среднее число процессов в состояниях R и D за 1, 5 и 15 минут |
| Tasks | Сколько процессов всего, работающих, спящих, остановленных, зомби |
| us | Время CPU на пользовательские процессы |
| sy | Время CPU на ядро (системные вызовы) |
| ni | Процессы с изменённым приоритетом |
| id | Простой CPU |
| wa | I/O wait: CPU простаивает, пока ждёт ответа диска |
| hi / si | Аппаратные / программные прерывания |
| st | Время, «украденное» гипервизором (важно в виртуалках) |
| MiB Mem / Swap | Память; в строке Mem колонка **avail Mem** это доступная оперативка (а не swap) |

Клавиши `top`: `1` по ядрам, `M` сортировка по памяти, `P` по CPU, `c` показать полную команду, `H` потоки, `k` убить, `q` выход. `htop`: F5 дерево, F6 сортировка, F9 kill.

### 6.2 Как читать load average

- Это **не проценты CPU**, а среднее число процессов, которые работают или ждут очереди (в Linux ещё и те, что ждут диск, состояние D). Ориентир: число ядер (`nproc`).
- Пример: 2 ядра. Load около 2: ядра заняты полностью, очереди почти нет. Заметно выше 2: очередь, перегрузка.
- **Почему три числа:** это 1, 5 и 15 минут, они показывают тренд. Если значение за 1 минуту больше, чем за 15, нагрузка растёт.
- Высокий load при **высоком `us`/`sy`** значит, что упёрлись в процессор. Высокий load при **низком CPU и большом `wa`** значит, что процессы ждут диск (состояние D).
- **Когда большой load не проблема:** например, сервер бэкапов, куда постоянно пишут данные: процессы копятся в D, а сервер работает нормально. А на сервере с сайтом высокий load скорее проблема. Поэтому смотрю не на число, а на то, что происходит с сервисами и что в очереди.
- Мой опыт: 10 процессов `yes > /dev/null &` на 2 ядрах дают load около 10, а каждый процесс занимает около 20% CPU. Однопоточный процесс не может занять больше одного ядра.

**iowait (`wa`)** это процент времени, когда CPU простаивает, потому что ждёт завершения операций ввода-вывода. Большое значение говорит о медленных или перегруженных дисках.

### 6.3 Глубокая диагностика

```bash
sar -q 1 5          # очередь выполнения (runq-sz), процессы (plist-sz), ldavg-1/5/15, blocked
vmstat 1            # r (очередь), b (заблокированные), swap, io, us/sy/id/wa
iostat -x 1         # загрузка дисков (await, %util)
iotop               # какие процессы больше всего пишут и читают (нужен root)
pidstat 1           # по процессам: CPU, память, диск
```

`sar` без интервала читает историю, а она копится, только если включён сбор (в Debian пакет `sysstat` может быть выключен, проверю `/etc/default/sysstat`).

Сеть: `ss -tulpn` (слушающие порты и процессы), `iftop` (трафик по соединениям), `nload` (график трафика).

**Кейс: сервер тормозит, а процессы вроде нормальные.** Мой порядок поиска:

1. `top`: вижу много `sy` (время ядра) и какой процесс его ест (допустим, systemd, PID 1).
2. `strace -c -p 1`: сводка системных вызовов, чаще всего `waitid` (systemd что-то постоянно запускает и ждёт).
3. `watch -n 1 'ps --ppid 1'`: какие процессы он порождает.
4. Нашёл подозрительный скрипт: `find / -name "имя" 2>/dev/null`.
5. Проверяю, откуда он запускается: cron, таймеры systemd (`systemctl list-timers`), файлы входа (`.profile`). Если файл подозрительный, это может быть чужой код (майнер и т.п.).

## 7. Память

### 7.1 Основы

- **Физическая память (RAM)** это оперативная память, энергозависимая.
- **Виртуальная память** это способ управления: у каждого процесса своё адресное пространство, и ядро (вместе с блоком процессора MMU) через таблицы страниц отображает его в реальную память. Благодаря этому процессы изолированы, программе можно «видеть» больше памяти, чем есть, а часть страниц можно вытеснить на диск (swap).
- **Page fault:** процесс обращается к странице, которой сейчас нет в памяти. Если доступ законный, ядро подгружает страницу. Если нет, процесс получает **SIGSEGV** (segmentation fault) и умирает.

```bash
free -h            # память (смотрю столбец available, а не free)
cat /proc/meminfo
ps -eo pid,rss,vsz,cmd --sort=-rss | head
```

| Термин | Смысл |
|---|---|
| RSS | Сколько памяти процесс реально держит в RAM |
| VSZ / VIRT | Виртуальный размер: сколько адресов процесс «запросил про запас». Это не реальное потребление, на него не опираюсь |
| shared | Память, общая для нескольких процессов (библиотеки, `tmpfs`) |
| page cache | Кэш файлов в RAM; ядро освобождает его по требованию |
| dirty pages | Страницы, изменённые в памяти, но ещё не записанные на диск (их сначала нужно сбросить на диск) |

**available и free.** Linux занимает свободную память кэшем (чтобы не читать диск заново), поэтому маленький `free` это нормально. `available` показывает, сколько реально можно отдать приложениям без swap (свободная память плюс кэш, который можно сбросить). На проблему указывают: `available` близок к нулю или в `dmesg -T` есть строки про `out of memory`.

### 7.2 Swap

**Как я это понимаю.** Swap это место на диске, куда ядро выгружает редко нужные страницы памяти, чтобы освободить RAM. Это не «аварийная память»: он помогает ядру лучше управлять кэшем и «анонимными» страницами (данными процессов, у которых нет файла на диске).

- Бывает **разделом** или **файлом**. Смотреть: `swapon --show`, `free -h`.
- Минус: диск в тысячи раз медленнее RAM. Если система постоянно гоняет страницы туда и обратно, она тормозит, и помогает только больше RAM.
- **swappiness** (`sysctl vm.swappiness`, по умолчанию 60) задаёт, насколько охотно ядро использует swap. Обычно значения 0–100 (в новых ядрах допускается и больше).
- Без swap OOM Killer срабатывает быстрее.
- Создать файл подкачки: `fallocate -l 2G /swapfile`, `chmod 600 /swapfile`, `mkswap /swapfile`, `swapon /swapfile`, строка в `/etc/fstab`.

Когда памяти мало, ядро действует так: сбрасывает кэш (его можно перечитать), записывает на диск грязные страницы и затем освобождает их, анонимные страницы выгружает в swap, а если и это не помогло, зовёт OOM Killer.

### 7.3 OOM Killer

- Включается, когда заканчивается память (и swap).
- Ядро выбирает процесс-жертву по оценке (`oom_score`, примерно пропорциональна доле памяти, которую занимает процесс, плюс поправка `oom_score_adj`) и убивает его SIGKILL.
- Защита: `oom_score_adj` от -1000 до 1000 (`/proc/PID/oom_score_adj`); для службы в unit-файле `OOMScoreAdjust=-1000`. Значение -1000 значит «не трогать».
- Следы: `dmesg -T | grep -i "out of memory"` или `journalctl -k | grep -i oom`.
- В Kubernetes, если контейнер превышает лимит памяти своей cgroup, его убивают: статус `OOMKilled`.

## 8. Изоляция и ограничения (основа контейнеров)

**Как я это понимаю.** Контейнер это обычные процессы Linux, которых изолируют (namespaces), ограничивают (cgroups) и лишают лишних прав (capabilities). Отдельной виртуальной машины нет.

### 8.1 cgroups (control groups)

Группировка процессов для **учёта и ограничения** ресурсов: CPU, память, ввод-вывод, число процессов.

- Современные дистрибутивы используют cgroup v2 (единое дерево в `/sys/fs/cgroup`). Файлы: `memory.max`, `cpu.max`, `pids.max`, `io.max`.
- systemd кладёт каждую службу в свою cgroup и может ограничить её (`MemoryMax=`, `CPUQuota=`).
- Docker и Kubernetes (`--memory`, `--cpus`, `limits`) реализуют ограничения через cgroups.
- Посмотреть: `systemd-cgls`, `systemd-cgtop`, `cat /proc/self/cgroup`.

**Квоты:**

- **CPU-квота** (`cpu.max`): сколько времени CPU группа может занять за период (например, «50000 100000» это 50% одного ядра).
- **Память** (`memory.max`): жёсткий предел, при превышении срабатывает OOM внутри группы.
- **Дисковые квоты:** отдельный механизм файловой системы, ограничивает место на пользователя или группу (`quota`, `edquota`, `repquota`).

### 8.2 Namespaces

Ограничивают то, **что процесс видит**.

| Namespace | Что изолирует |
|---|---|
| pid | Нумерацию процессов (в контейнере свой PID 1) |
| net | Сетевые интерфейсы, маршруты, порты |
| mnt | Точки монтирования и файловое дерево |
| uts | Имя хоста и домена |
| ipc | Общую память, очереди |
| user | Пользователей и права (root в контейнере не root на хосте) |
| cgroup | Вид дерева cgroup |
| time | Системные часы (с ядра 5.6) |

```bash
lsns                                         # какие namespaces есть
ls -l /proc/$$/ns                            # namespaces моего процесса
sudo unshare --pid --fork --mount-proc bash  # новый pid-namespace: в ps только пара процессов
sudo unshare --uts bash                      # свой hostname: hostname test, затем exit
```

**Запомнить:** cgroups говорят **сколько** можно, namespaces говорят **что видно**. 
**Моя аналогия:** cgroups это лимит на счёте, namespaces это отдельная комната со шторами.

### 8.3 Capabilities

Права root разбиты на отдельные «возможности», которые можно выдавать по одной.

| Capability | Что разрешает |
|---|---|
| `CAP_NET_BIND_SERVICE` | Слушать порты ниже 1024 |
| `CAP_NET_ADMIN` | Настраивать сеть |
| `CAP_NET_RAW` | Сырые сокеты |
| `CAP_CHOWN` | Менять владельца файлов |
| `CAP_DAC_OVERRIDE` | Обходить проверку прав на файлы |
| `CAP_KILL` | Посылать сигналы чужим процессам |
| `CAP_SYS_ADMIN` | Очень широкий набор («почти root»), выдавать не стоит |

```bash
getpcaps $$                  # возможности процесса (пакет libcap2-bin)
grep Cap /proc/self/status   # то же в виде масок
getcap /путь/к/программе
sudo setcap 'cap_net_bind_service=+ep' /путь/к/программе   # порт 80 без root
```

Контейнеры по умолчанию получают урезанный набор, лишнее убирают через `--cap-drop`.

## 9. Загрузка системы (от кнопки питания до логина)

**Как я это понимаю.** Включаю питание, прошивка проверяет железо и находит загрузчик, загрузчик грузит ядро, ядро запускает первый процесс (PID 1), а тот поднимает все службы и показывает вход. Это прямой ответ на вопрос «опиши загрузку Linux».

| Шаг | Что происходит |
|---|---|
| 1. Прошивка (BIOS или UEFI) | **POST** (Power-On Self-Test): проверка CPU, RAM и устройств. Затем выбор загрузочного устройства |
| 2. Поиск загрузчика | BIOS читает **MBR** (первые 512 байт диска: 446 байт кода загрузчика, 64 байта таблицы разделов, 2 байта подписи). UEFI читает файл `.efi` из раздела **ESP** (EFI System Partition) |
| 3. Загрузчик (GRUB) | Первая стадия крошечная (в 446 байт много не поместится) и запускает вторую. Показывает меню, грузит в память ядро и initramfs, передаёт ядру параметры (`/proc/cmdline`) |
| 4. Ядро (kernel) | Распаковывается, инициализирует CPU, память, планировщик, драйверы; временно монтирует initramfs |
| 5. initramfs | Подгружает драйверы диска, LVM, RAID, шифрования, находит и монтирует настоящий корень `/`, затем передаёт управление |
| 6. PID 1 | Ядро запускает первый процесс (`/sbin/init`, в Debian ссылка на systemd) |
| 7. systemd | Монтирует ФС из `/etc/fstab`, запускает службы до цели `default.target` |
| 8. Вход | Появляется приглашение (getty, графический менеджер входа или SSH), затем читаются файлы оболочки (`.bashrc`, `.profile`) |

**BIOS и UEFI.**

| | BIOS | UEFI |
|---|---|---|
| Режим работы | 16-разрядный, мало памяти | 32 или 64 бита, большое адресное пространство |
| Разметка диска | MBR (разделы до примерно 2 ТиБ) | GPT (огромные диски, до ~9.4 ЗБ) |
| Загрузчик | Код в MBR | Файл `.efi` в разделе ESP |
| Возможности | Минимум | Графический интерфейс, **Secure Boot** (проверка подписи загружаемого кода), загрузка по сети |

**Термины:**

- **vmlinuz**: сжатый исполняемый образ ядра, лежит в `/boot/vmlinuz-<версия>` (несжатый называется `vmlinux`).
- **initramfs** (в Debian `/boot/initrd.img-<версия>`): небольшая временная корневая ФС в RAM. Нужна, потому что ядру, прежде чем смонтировать настоящий корень, нужны драйверы и скрипты, которых ещё нет на диске. Пересоздать: `sudo update-initramfs -u`.
- **Ядро (kernel)**: самый низкий слой ПО, управляет процессами, памятью, устройствами, ФС и сетью, предоставляет системные вызовы.
- **Загрузчик**: программа, которая загружает ОС после POST. Настройка GRUB: `/etc/default/grub`, применить `sudo update-grub`.
- **Kernel panic**: критическая ошибка ядра, после которой оно не может безопасно продолжать, система останавливается («Kernel panic - not syncing»). Типичные причины: не нашёлся или не смонтировался корень (неверный `root=` или `/etc/fstab`, нет драйвера диска в initramfs), битый initramfs, сбойный драйвер, проблемы с RAM, падение PID 1. Что делаю: выбираю в GRUB более старое ядро, загружаюсь с live-USB и чиню (fstab, initramfs, GRUB), проверяю память. Менее тяжёлая ошибка называется oops (система часто работает дальше). Автоперезагрузка после panic: параметр `kernel.panic`.

Полезные команды: `uname -r` (версия ядра), `cat /proc/cmdline`, `dmesg` и `journalctl -k` (сообщения ядра), `journalctl -b` (логи текущей загрузки), `systemd-analyze` и `systemd-analyze blame` (время загрузки).

**Про WSL:** в WSL2 нет BIOS и GRUB, ядро поставляет и запускает сама WSL.

## 10. Системы инициализации, systemd, службы, логи

### 10.1 Зачем нужна система инициализации

**Как я это понимаю.** После загрузки ядра кто-то должен поднять всё остальное: смонтировать диски, запустить службы, следить за ними. Это делает процесс инициализации. Он запускается ядром первым (PID 1) и работает, пока работает система.

| | SysV init | systemd |
|---|---|---|
| Идея | Уровни запуска (runlevels) и shell-скрипты в `/etc/init.d` | Декларативные unit-файлы, зависимости, параллельный запуск |
| Запуск служб | Последовательный | Параллельный |
| Слежение за службой | Почти нет | Есть (через cgroups), `Restart=` |
| Где встречается | Старые системы | Практически везде сейчас (Debian, Ubuntu, RHEL) |

**Что говорю на собесе: чем systemd лучше init.**

- Запускает службы **параллельно** с учётом зависимостей, загрузка быстрее (быстрее не из-за «особенностей процессора», а из-за зависимостей и socket activation).
- Служба описывается коротким unit-файлом вместо длинного shell-скрипта.
- Сам перезапускает упавшие службы (`Restart=`).
- Единый удобный инструмент для логов (`journalctl`) и управления (`systemctl`).
- Следит за всеми процессами службы через cgroups, умеет их ограничивать.
- Есть таймеры (замена cron) и цели (targets) вместо runlevels.

**Уровни запуска (runlevels) и targets.**

| Runlevel | Смысл | Аналог в systemd |
|---|---|---|
| 0 | Выключение | `poweroff.target` |
| 1 | Однопользовательский режим (восстановление, работает только root) | `rescue.target` |
| 2 | Многопользовательский без сетевых ФС (в Debian стандартный многопользовательский) | `multi-user.target` |
| 3 | Многопользовательский с сетью (нормальный режим сервера без графики) | `multi-user.target` |
| 4 | Не используется в большинстве систем | |
| 5 | Графический режим | `graphical.target` |
| 6 | Перезагрузка | `reboot.target` |

Команды: `systemctl get-default`, `systemctl set-default multi-user.target`, `systemctl isolate rescue.target`.

**Как понять, что в системе systemd:** `ps -p 1 -o comm=` (должно быть `systemd`), `readlink /proc/1/exe`, `stat /sbin/init` (ссылка на systemd), наличие каталога `/run/systemd/system/`.

### 10.2 Команды systemd

```bash
systemctl status имя          # состояние, код выхода, последние строки лога
sudo systemctl start имя      # запустить сейчас
sudo systemctl stop имя
sudo systemctl restart имя
sudo systemctl reload имя     # перечитать конфиг без остановки (если служба умеет)
sudo systemctl enable имя     # запускать при загрузке
sudo systemctl enable --now имя   # и включить, и запустить
sudo systemctl disable имя
systemctl is-enabled имя
systemctl list-units --type=service
systemctl --failed            # упавшие службы
systemctl cat имя             # показать unit-файл
sudo systemctl daemon-reload  # после правки unit-файла
systemctl list-timers         # таймеры
```

`start` и `enable` независимы: запущена сейчас или включена при загрузке это разное.

**Простой unit-файл** (`/etc/systemd/system/имя.service`, правлю через `sudoedit`):

```ini
[Unit]
Description=Моя служба
After=network.target

[Service]
ExecStart=/home/user/script.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Зависимости: `After=` задаёт порядок, `Wants=` и `Requires=` задают необходимость. `Restart=`: `no`, `on-failure`, `always`. Лимиты: `MemoryMax=`, `LimitNOFILE=`, `OOMScoreAdjust=`.

### 10.3 Служба упала: порядок действий

1. `systemctl status имя`: состояние (`failed`), код выхода, последние строки.
2. `journalctl -u имя -n 50` (ещё `-f` следить, `-b` с последней загрузки, `--since "1 hour ago"`).
3. Ошибки по системе: `journalctl -p err -n 30`.
4. `systemctl cat имя`: что именно запускается.
5. Типичные причины: ошибка в конфиге или пути в `ExecStart`, занятый порт (`ss -tulpn`), неверные права, нехватка места или памяти, лимит файлов.
6. После исправления: `sudo systemctl daemon-reload`, затем `restart`.

### 10.4 Логи

- `journalctl` читает журнал systemd (journald). Логи прошлых загрузок (`-b -1`) доступны, только если журнал сохраняется на диск (зависит от `Storage=`, проверю у себя).
- `/var/log/*`: текстовые логи. В Debian `rsyslog` может быть не установлен, тогда `/var/log/syslog` нет, и всё в journald (проверю `ls /var/log`).
- **logrotate**: по расписанию ротирует логи (сжимает, удаляет старые), настройки в `/etc/logrotate.conf` и `/etc/logrotate.d/`.
- `tail -f файл` следить, `grep -i error файл` искать.

**Как посмотреть, что служба пишет в stdout:**

1. Если это служба systemd, её stdout и stderr по умолчанию попадают в журнал: `journalctl -u имя`.
2. Найти, куда пишет процесс: `lsof -p PID | grep -E 'w|u'` или `ls -l /proc/PID/fd`.
3. Перехватить записи: `strace -e write -s 9999 -p PID` (замедляет процесс, вывод в сыром виде).

## 11. VFS, диски и файловые системы

### 11.1 VFS и псевдофайловые системы

**VFS** (Virtual File System) это слой в ядре, который даёт программам единый интерфейс (`open`, `read`, `write`, `close`) к любым файловым системам: ext4, xfs, btrfs, tmpfs (в RAM), NFS (по сети), `/proc`, `/sys`. Поэтому `cat` одинаково работает с файлом на диске, с `/proc/cpuinfo` и с файлом на сетевом диске. Основные объекты VFS: superblock (сведения о ФС), inode (описание файла), dentry (запись «имя в каталоге», кэшируется), file (открытый файл).

**Псевдофайловая система**: файлов на диске нет, записи ядро создаёт на лету, содержимое живёт в памяти ядра. Примеры: `/proc` (процессы), `/sys` (устройства и параметры ядра), `/dev` (устройства, часто devtmpfs), `tmpfs`.

### 11.2 Блочные и символьные устройства

| | Блочные | Символьные |
|---|---|---|
| Данные | Блоками, **произвольный доступ** | Потоком байт, последовательно |
| Примеры | Диски, разделы, CD, RAM-диски | Клавиатура, мышь, последовательные порты, терминалы, `/dev/null`, `/dev/zero` |
| В `ls -l /dev` | Первая буква `b` | Первая буква `c` |
| Что делают | Монтируют ФС, читают и пишут блоки, создают разделы | Читают и пишут байты |

Блочные устройства ядро буферизует и кэширует. Посмотреть: `lsblk`.

### 11.3 Место на диске, inode

```bash
df -h               # сколько места свободно на ФС
du -sh *            # сколько занимает каждая папка здесь
ncdu /var           # интерактивно: кто съел место
df -i               # сколько свободно inode
lsblk               # диски и разделы
blkid               # UUID и тип ФС
findmnt             # что куда смонтировано
```

**inode** это «карточка» файла: хранит права, владельца, размер, времена и **где лежат данные**. **Имени файла там нет**: имя хранится в каталоге, который связывает имя с номером inode (`ls -i`). Каждая ФС имеет свою таблицу inode (в ext2/3/4 таблицы лежат по группам блоков). Количество inode на ext4 фиксируется при создании ФС (`mkfs.ext4 -N` или `-i`), добавить потом нельзя. В XFS, Btrfs и ZFS inode динамические, их создаётся столько, сколько нужно.

**«No space left on device», а место есть: что проверяю.**

1. `df -h`: нет ли переполнения на самом деле.
2. `df -i`: если inode 100%, виной миллионы мелких файлов. Найти: `sudo du --inodes -x / 2>/dev/null | sort -rn | head`.
3. **Квота:** если создать файл не может обычный пользователь, а root может, смотрю `quota -v user`. Ещё причина: ext4 резервирует около 5% места для root (`tune2fs -l /dev/sdX | grep -i reserved`, менять `tune2fs -m`).
4. Другой раздел переполнен (`/var`, `/tmp`).

**`df` показывает 20 ГБ занято, а `du` насчитал 20 МБ.** Причины:

- Файл удалён, но его всё ещё держит открытым процесс: имя пропало, а inode и данные остаются, пока процесс жив. Ищу `lsof +L1` (или `lsof -a +L1 /var`). Освобождаю перезапуском процесса или `truncate -s 0 /proc/PID/fd/N`.
- Под точкой монтирования лежат файлы: когда в папку смонтировали диск, прежнее содержимое папки скрыто, но место занимает.

### 11.4 Создание ФС, монтирование, fstab

```bash
sudo mkfs -t ext4 /dev/sdb1        # то же, что mkfs.ext4; стирает данные!
sudo mkfs.ext4 -L метка -m 1 -b 4096 -N число_inode /dev/sdb1   # метка, % резерва для root, размер блока, число inode
sudo mount /dev/sdb1 /mnt/data     # смонтировать
sudo umount /mnt/data
mount -t ext4                      # показать только ext4 (mount без аргументов покажет все)
findmnt; cat /proc/mounts          # ещё способы посмотреть смонтированное
sudo mount -a                      # применить fstab (проверка файла без перезагрузки)
```

- `/etc/fstab`: список ФС, которые монтируются при загрузке. Строка: `UUID=... /mnt/data ext4 defaults 0 2` (устройство, точка, тип, опции, dump, порядок fsck). Ошибка может сломать загрузку, поэтому после правки делаю `sudo mount -a`, а для необязательных дисков добавляю `nofail`.
- **Какие процессы используют раздел** (когда `umount` пишет «target is busy»): `fuser -mv /точка` или `lsof +f -- /точка`.

### 11.5 Проверка и ремонт ФС

- Если автопроверка при загрузке не справилась, система уходит в однопользовательский режим и просит вручную запустить `fsck`.
- **`fsck` запускаю только на размонтированной ФС** (корень проверяю из rescue-режима или с live-USB). Сначала бэкап. Пробный запуск без изменений: `fsck -n`. Для ext: `e2fsck -f /dev/sdX`.
- Признаки проблем диска: ошибки ввода-вывода в `dmesg`, состояние SMART (`smartctl -a /dev/sdX`, пакет smartmontools).

### 11.6 ext4 или xfs

| | ext4 | xfs |
|---|---|---|
| Сильная сторона | Универсальная, привычная, по умолчанию в Debian | Очень большие ФС и файлы, параллельные нагрузки, быстрые операции с большими данными |
| Размер ФС | Увеличить можно, **уменьшить можно** (на размонтированной) | Увеличить можно (`xfs_growfs`), **уменьшить нельзя** |
| inode | Фиксируются при создании | Динамические |

Эти различия я помню твёрдо. Любые конкретные цифры лимитов и «xfs хуже переживает аварии» это мнения из чужого опыта, на собесе говорю осторожно: выбор зависит от нагрузки.

**Как определить, на каком физическом диске раздел:** `findmnt -no SOURCE /home` (какое устройство), `lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINT`, `smartctl -i /dev/sda` (модель и серийный номер).

### 11.7 LVM и RAID

**LVM** (Logical Volume Manager) это слой над физическими дисками: цепочка **PV** (физический том, диск или раздел) → **VG** (группа томов) → **LV** (логический том, на нём ФС). Размер можно менять на лету, добавлять диски, делать снимки.

```bash
pvs; vgs; lvs                              # посмотреть
sudo lvcreate -L 10G -n data vg0           # создать том
sudo lvextend -r -L +5G /dev/vg0/data      # увеличить том (-r сразу расширит и ФС)
```

**RAID** объединяет диски для скорости и/или надёжности.

| Уровень | Как устроен | Мин. дисков | Сколько дисков может отказать | Полезная ёмкость |
|---|---|---|---|---|
| RAID 0 | Чередование, без защиты | 2 | 0 (потеряю всё) | все диски |
| RAID 1 | Зеркало | 2 | все, кроме одного | половина (для двух дисков) |
| RAID 5 | Чередование и чётность | 3 | 1 | N − 1 |
| RAID 6 | Чередование и двойная чётность | 4 | **2** | N − 2 |
| RAID 10 | Зеркала плюс чередование | 4 | по одному в каждой зеркальной паре | половина |

Программный RAID в Linux: `mdadm`, состояние `cat /proc/mdstat`. Аппаратный RAID создаётся контроллером до установки ОС. При замене диска в RAID 5 идёт долгая перестройка, и если в это время откажет ещё один диск, данные потеряны (поэтому для больших дисков берут RAID 6). **RAID не заменяет бэкап**: он не спасёт от удаления файлов по ошибке, вирусов, пожара и сбоя контроллера.

## 13. Типовые поломки (практика траблшутинга)

**Сервер не отвечает, а я не в ЦОДе.** Удалённое управление: IPMI (iDRAC, iLO), KVM-over-IP, консоль через последовательный порт, либо тикет в ЦОД, чтобы посмотрели на месте.

**Веб-сервер отдаёт 502 (Bad Gateway).** nginx (прокси) получил от вышестоящего сервера некорректный ответ или не смог подключиться. Что делаю:

1. Лог ошибок nginx (`error_log`), смотрю причину.
2. В конфиге смотрю `proxy_pass`: куда он идёт.
3. Жива ли служба за ним и слушает ли порт (`systemctl status`, `ss -tulpn`), отвечает ли напрямую (`curl` на её адрес).
4. Смотрю логи самого приложения, ресурсы сервера. Подход тот же для всех 5xx. Отличие: 504 это таймаут ответа, а 502 это плохой ответ или отказ в соединении.

**Файл с нечитаемым содержимым.** `file имя` покажет, что это (архив, исполняемый файл, текст), `file -i` дополнит типом и кодировкой.

**Запуск файла даёт «No such file or directory», хотя файл есть.** Причины:

- файл или путь к нему не существует, либо это битая символическая ссылка;
- в первой строке (shebang) указан интерпретатор, которого нет в системе;
- **в скрипте окончания строк CRLF (скрипт, написанный на Windows)**: система ищет интерпретатор `bash\r`. Проверяю `file script.sh`, лечу `dos2unix script.sh` или `sed -i 's/\r$//' script.sh`;
- 32-битный бинарник без нужных библиотек, нет динамического загрузчика.

**Программа не может найти свой конфигурационный файл.** `strace -f -e trace=openat,stat программа 2>&1 | grep -i conf` покажет, где она ищет. Либо у программы есть режим подробного вывода (`-v`, `--verbose`) или команда вида `--help`, которая печатает пути по умолчанию.

**Бинарник запускается и сразу падает.** `strace ./программа` (смотрю последние системные вызовы перед падением: нет файла, нет прав, SIGSEGV), `ldd ./программа` (не хватает ли библиотек), `dmesg` и `journalctl -k` (записи ядра), при `core dumped` смотрю core-файл (`coredumpctl`).

**Нагрузка 900 при нормальной работе сервера.** Смотрю, что вообще важно и что работает. Если основные сервисы живы, высокий load может быть от очереди медленных операций (диск, сеть), смотрю `wa` и процессы в состоянии D. На сервере с активными приложениями высокий load скорее проблема, на сервере бэкапов нет.

**Сервер тормозит под нагрузкой.** Кейс про `sy` и systemd разобран в разделе 6.3.

## 14. Что неверно в чужих сборниках (чтобы не заучить ошибку)

Пока читал источники, нашёл неточности. Фиксирую правильные версии:

| Было в источнике | Как правильно |
|---|---|
| SIGSTOP = 10 | SIGSTOP = **19**, а 10 это SIGUSR1 |
| SIGKILL убивает дочерние процессы | Не убивает: потомки становятся сиротами, их подбирает PID 1 |
| FIFO это полный дуплекс | И пайп, и FIFO работают в **одну сторону** |
| В строке `avail Mem` swap | `avail Mem` это доступная оперативная память |
| iowait измеряется в числе потоков | iowait это процент времени CPU в ожидании ввода-вывода |
| systemd быстрее из-за особенностей процессора | Быстрее из-за параллельного запуска по зависимостям |
| `limits.conf` задаёт лимит для службы | Для службы systemd лимит ставят `LimitNOFILE=` в unit-файле |

## 15. Мои грабли и частые ошибки в ответах

- Load average это **не** «использование ядер», а среднее число процессов в R и D за 1, 5 и 15 минут.
- «No space left on device»: команда **`df -i`**, а не `du -i`.
- Зомби и сироту путаю: **зомби** это умерший потомок, запись которого не забрал родитель; **сирота** это живой потомок умершего родителя.
- `kill` по умолчанию шлёт 15 (SIGTERM), а `kill -9` это SIGKILL.
- Жёсткая ссылка это ещё одно **имя** того же inode (растёт счётчик ссылок), а не новый inode и не PID.
- `fork()` копирует процесс, `exec()` **заменяет программу** в процессе (не «перерождает в новую версию»).
- OOM: `-1000` пишется в `oom_score_adj` процесса или в `OOMScoreAdjust=` unit-файла, а не в общий конфиг.
- Из загрузки у меня выпадал загрузчик (GRUB) между прошивкой и ядром.
- Зомби не убить, потому что он уже мёртв; причина существования зомби в том, что родитель не вызвал `wait()`.

## 16. Шпаргалка: ситуация и команда

| Ситуация | Команда |
|---|---|
| Кто съел процессор или память | `top`, `htop`, `ps aux --sort=-%cpu` / `--sort=-%mem` |
| Нагрузка на диски | `iostat -x 1`, `iotop` |
| Нет места на диске | `df -h`, `df -i`, `du -sh *`, `ncdu`, `lsof +L1` |
| Служба упала | `systemctl status`, `journalctl -u имя -n 50` |
| Кто слушает порт | `sudo ss -tulpn` |
| Какие файлы открыл процесс | `lsof -p PID`, `ls -l /proc/PID/fd` |
| Что делает процесс на уровне ядра | `strace -p PID`, `strace -c команда` |
| Остановить процесс вежливо / жёстко | `kill PID` / `kill -9 PID` |
| Почему сервер тормозит | `top` (смотрю us, sy, wa), `uptime`, `vmstat 1`, `sar -q 1 5` |
| Память кончается | `free -h`, `dmesg -T \| grep -i "out of memory"` |
| Проверить права по пути | `namei -l путь` |
| Скрипт отлаживать | `bash -x script.sh`, `set -x` |
| Кто вошёл в систему | `who`, `w`, `last` |
| Какая система инициализации | `ps -p 1 -o comm=` |
| Что за файл | `file имя`, `stat имя` |
